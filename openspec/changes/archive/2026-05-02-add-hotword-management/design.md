## Context

当前聊天页快捷问题由 `ChatView.vue` 中的 `quickPrompts` 静态数组提供，无法在运行期维护，也无法根据租户隔离或业务热点更新。项目后端已使用 Spring Boot、MyBatis Plus、MySQL 与 `StringRedisTemplate`，已有聊天消息缓存等 Redis 回源 MySQL 的模式，可复用为热词的双级读取策略。

该变更需要新增跨前后端能力：后端提供热词管理与随机读取 API，MySQL 负责权威数据，Redis 负责启用热词池缓存和预设答案缓存，前端新增“热词管理”页面，并改造聊天页快捷问题区域支持刷新和热词标记提交。

## Goals / Non-Goals

**Goals:**
- 将聊天快捷问题从前端硬编码迁移到后端热词服务。
- 提供“热词管理”页面，支持新增、编辑、启停、删除、分页查询和刷新。
- 使用 MySQL 作为权威存储，Redis 作为启用热词池缓存，读取时优先 Redis、缺失时回源 MySQL。
- 聊天页每次随机展示 3 条启用热词，并支持用户点击刷新重新获取。
- 热词可配置唯一标记和预设答案，聊天页发送热词时携带标记，后端命中后直接返回预设答案。
- 按租户隔离热词数据，避免跨租户读取或管理。
- 新增数据库字段、实体类字段、枚举值时按项目规则添加中文注释。

**Non-Goals:**
- 不引入新的搜索引擎或推荐算法。
- 不基于用户画像、会话上下文或点击行为做个性化推荐。
- 不改变普通聊天问答、RAG 检索、反馈提交等已有业务流程；仅热词标记命中时新增直答分支。
- 不实现热词点击统计排行榜，后续如需要可单独扩展。

## Decisions

### 1. 数据模型采用独立 `chat_hotword` 表

新增独立表保存热词标记、热词内容、预设答案、分类、权重、启用状态、排序号、租户、创建/更新时间和逻辑删除标记。这样可以避免把运营配置写入前端源码，也不会污染聊天消息或知识库表。

备选方案是使用通用配置表，但热词需要分页管理、启停、随机读取、权重和缓存失效，独立表更清晰，也便于后续扩展统计字段。

### 2. 读取链路采用 Redis 启用热词池 + MySQL 回源

随机读取接口先从 Redis 读取当前租户的启用热词池，Redis 不存在或为空时查询 MySQL 中启用且未删除的热词并回填 Redis。管理端新增、编辑、启停、删除后主动删除对应租户 Redis key，让下一次读取回源并刷新。

Redis value 建议使用 JSON 数组，key 形如 `legal:chat:hotword:enabled:{tenantId}`，TTL 可设置为 1 天。随机抽取在服务端完成，确保聊天页和其他未来入口复用同一逻辑。预设答案单独使用 `legal:chat:hotword:answer:{tenantId}:{hotwordKey}` 缓存，命中热词直答时优先读取 Redis，缺失时回源 MySQL 并回填。

### 3. 随机读取固定返回 3 条，兼容不足 3 条场景

接口默认返回最多 3 条启用热词。启用热词少于 3 条时返回全部；没有热词时返回空数组，前端显示空态或隐藏快捷问题区域。

如果后续需要可通过 `limit` 参数扩展，但当前聊天页固定使用 3 条以满足需求并保持交互稳定。

### 4. 管理 API 与随机 API 分离

管理 API 面向“热词管理”页面，提供分页、创建、更新、启停、删除。随机 API 面向聊天页，只返回可展示的启用热词，避免把管理字段暴露给普通展示场景。

建议接口：
- `GET /api/hotwords/random?limit=3`：随机获取启用热词。
- `GET /api/hotwords`：分页查询热词。
- `POST /api/hotwords`：新增热词。
- `PUT /api/hotwords/{id}`：编辑热词。
- `POST /api/hotwords/{id}/status`：启停热词。
- `DELETE /api/hotwords/{id}`：删除热词。

### 5. 前端新增管理页并改造聊天页

新增 `HotwordView.vue` 作为“热词管理”页面，接入现有导航和 API 客户端风格。聊天页在 `onMounted` 中加载热词，并在快捷问题区域提供“换一组”按钮，点击后重新请求随机接口。

### 6. 热词预设答案在 `askStream` 中前置判断

聊天页点击热词后保存随机接口返回的 `hotwordKey`，发送 `askStream` 时随问题一起提交。后端在保存用户消息后、执行普通问答缓存与 RAG 检索前，根据当前租户、启用状态、未删除状态和 `hotwordKey` 查询预设答案；命中时直接通过 SSE 返回 `answer`、空 `citations` 和 `done`，并持久化助手消息。用户手动编辑输入内容时前端清空热词标记，避免误触发直答。

## Risks / Trade-offs

- **Redis 缓存与 MySQL 短暂不一致** → 管理写操作成功后删除租户热词池缓存和对应预设答案缓存，读取接口负责回填，保证最终一致。
- **随机读取性能受热词池大小影响** → Redis 中缓存轻量 VO 列表，随机抽取只在内存列表完成；热词数量预期较小，性能可控。
- **没有启用热词导致聊天页无快捷问题** → 前端显示友好空态或隐藏 chips，管理页可提示创建热词。
- **跨租户数据泄漏风险** → 所有查询、写入、缓存 key 都必须带 `tenantId` 条件，管理接口也只能操作当前租户数据，预设答案查询同样必须限定当前租户。
- **热词标记误命中风险** → 前端仅在点击热词时携带标记，用户手动输入或编辑时清空标记；后端只在标记存在且热词启用、未删除时直答。
- **误删热词影响运营配置** → 前端删除按钮必须二次确认，后端建议逻辑删除而非物理删除。

## Migration Plan

1. 在 schema 中新增 `chat_hotword` 表，并为每个字段添加中文注释；热词标记和预设答案后续通过列迁移补齐到运行环境。
2. 新增实体、Mapper、DTO、VO、Service、Controller，并为实体字段添加中文注释。
3. 初始化可选默认热词数据，确保聊天页上线后不为空。
4. 前端新增“热词管理”页面与导航入口。
5. 改造聊天页加载随机热词、刷新热词和携带热词标记发送。
6. 改造 `askStream` 热词直答分支，并验证 Redis 预设答案缓存。
7. 运行后端编译/测试与前端构建验证。

回滚策略：保留前端默认兜底热词或在接口失败时隐藏热词区域；后端变更可通过禁用导航入口和停止调用新增 API 规避影响。数据库表独立新增，不影响已有聊天问答数据。

## Open Questions

- 热词是否需要区分业务分类，例如“劳动合同”“合同审查”“报销合规”？当前设计保留分类字段，但随机读取默认不按分类过滤。
- 是否需要系统默认热词与租户自定义热词合并展示？当前优先按租户隔离实现，后续可扩展 `tenantId=0` 的系统热词池。
