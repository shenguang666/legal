## Context

当前系统已经具备文档上传、文本抽取、切片与知识库索引能力：后端通过 `KnowledgeController` 和 `KnowledgeService` 完成文档导入，使用 `DocumentTextExtractor` 基于 Tika 提取文本，并将结果落到 `kb_document` / `kb_chunk`。前端已有 `KnowledgeView` 管理文档导入和索引。

合同条款风险识别是一个跨文档解析、业务规则校验、风险聚合和前端审阅的新增能力，既要复用现有文档处理链路，也要为后续规则扩展和人工复核保留结构化结果与可解释证据。系统还需要保持现有多租户、幂等请求和异步任务处理模式的一致性。

## Goals / Non-Goals

**Goals:**
- 基于现有文档导入能力，对合同文本执行结构化字段抽取。
- 对抽取字段执行企业规则校验，识别缺失项、冲突项和异常值。
- 生成可解释的风险摘要、风险项、证据片段和审阅详情，并可通过接口和页面查询。
- 通过异步任务和持久化结果避免长请求阻塞，支持失败重试与重复分析控制。

**Non-Goals:**
- 首期不建设通用可视化规则编排器或复杂 DSL 编辑器。
- 首期不覆盖扫描件 OCR 增强、图像版式识别或手写内容识别。
- 首期不提供自动改写合同、自动批准流程或完整合同生命周期管理。

## Decisions

### 1. 复用 `kb_document` 作为合同审阅输入源
合同风险审阅直接引用已导入的知识库文档，不重复建设新的上传存储链路。新增的合同审阅聚合以 `document_id` 和 `doc_version` 作为输入标识，并在独立表中保存审阅结果、抽取字段和风险项。

**Rationale:** 现有系统已经解决了文档上传、文本抽取、幂等和租户隔离问题，复用 `kb_document` 可以减少重复逻辑，并让文档可检索和文档可审阅共用同一份文档基线。

**Alternatives considered:**
- 单独建设合同上传模块：会导致文档重复存储、权限重复实现、维护成本更高。
- 仅以内存结果返回不落库：无法支持复核、追踪、重跑和前端详情页。

### 2. 使用异步审阅任务而不是同步接口内完成分析
新增合同审阅任务表/出站表，接口负责创建或触发审阅任务，后台 worker 负责执行文本分段、字段抽取、规则校验、风险聚合和结果落库。审阅状态至少包含 `PENDING`、`PROCESSING`、`COMPLETED`、`FAILED`。

**Rationale:** 合同解析和风险识别可能依赖多阶段处理或大模型调用，同步请求容易超时，也不利于失败重试和状态展示。

**Alternatives considered:**
- 同步分析后直接返回结果：实现简单，但对长文档和复杂规则不稳定。
- 仅依赖定时全量扫描：反馈不及时，用户体验较差。

### 3. 采用规则/模式抽取 + 语义抽取补充的混合抽取策略
对于金额、日期、币种、编号等显式字段，优先使用确定性解析器和模式匹配；对于责任条款、报销项目、条款冲突等语义性更强的内容，允许通过大模型或语义抽取器补充识别。每个字段结果都必须保存 `fieldCode`、`fieldName`、`rawValue`、`normalizedValue`、`status`、`confidence`、`evidenceText`、`sourceChunkRef`、`extractorType`。

**Rationale:** 纯规则方式难以覆盖复杂条款语义，纯大模型方式又存在不稳定和不可追踪的问题，混合方案更适合合同审阅首期版本。

**Alternatives considered:**
- 纯正则/模板：对责任条款和矛盾识别覆盖不足。
- 纯大模型抽取：可解释性和一致性较弱，调试成本高。

### 4. 采用可插拔校验器而不是首期通用规则 DSL
规则能力按校验类型组织为可插拔校验器，例如必填校验、一致性校验、阈值校验、日期顺序校验、条款冲突校验。规则定义保存规则编码、适用字段、严重级别、参数和启用状态，执行时产出规则命中记录与解释信息。

**Rationale:** 用户需要基于企业规则的能力，但首期更适合先落地一套可维护的规则执行框架，再逐步演进到配置化或 UI 化。

**Alternatives considered:**
- 将所有规则硬编码在单一 service：短期快，但扩展成本高。
- 直接引入复杂 DSL：实现成本和学习成本过高，不适合首期。

### 5. 风险结果以审阅摘要 + 风险项 + 字段明细三层模型对外提供
查询接口返回合同审阅摘要（总体风险等级、命中数量、关键提示）、字段抽取明细（值、状态、证据、置信度）和风险项明细（规则码、严重级别、解释、关联字段、证据片段）。前端新增独立合同风险审阅页面，或从现有知识库页面跳转到审阅详情。

**Rationale:** 用户既需要快速看总体风险，也需要下钻到字段和条款证据，三层模型兼顾列表展示和问题定位。

**Alternatives considered:**
- 仅返回自然语言总结：无法支撑人工复核和后续自动化处理。
- 仅返回原始规则命中：业务可读性不足。

## Risks / Trade-offs

- **抽取结果存在波动**  通过证据片段、置信度、缺失状态和可重跑能力降低误判影响。
- **不同企业规则差异大**  首期提供默认规则模板和版本化规则定义，后续再扩展租户级配置能力。
- **长文档分析成本较高**  使用异步任务、分段处理和增量重跑，避免接口阻塞。
- **误报/漏报影响业务信任**  在页面中展示解释与命中依据，并保留人工复核入口与状态。
- **文档更新后结果失效**  将审阅结果绑定 `doc_version`，文档版本变化时要求重新审阅。

## Migration Plan

1. 在 `schema.sql` 中新增合同审阅相关表结构，包括审阅主表、字段结果表、风险项表以及任务/规则定义表。
2. 新增后端 API、服务、worker 和领域对象，但保持功能默认仅对具备权限的用户开放。
3. 前端新增合同风险审阅入口和详情视图，先支持对已导入文档手动触发分析。
4. 上线后不强制回填历史文档，历史文档由用户按需触发首次审阅。
5. 如需回滚，可关闭审阅入口与异步消费逻辑，保留新增表结构但不再写入新数据。

## Open Questions

- 首期是否需要提供租户自定义规则维护界面，还是仅提供预置规则与后端配置。
- 合同审阅是在文档导入后自动触发，还是由用户手动点击开始审阅。
- 对扫描版 PDF 是否需要在后续版本补充 OCR 增强或版面理解能力。
