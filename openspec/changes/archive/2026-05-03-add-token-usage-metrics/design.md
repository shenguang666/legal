## 背景

当前问答链路已经在 `chat_message.token_usage` 记录单条消息的 Token 消耗，其中流式回答和 RAG 回答会写入模型返回的总 Token 数，用户消息与预设答案通常为 0。`chat_message` 本身不包含租户和用户字段，需要通过 `chat_session.session_id` 关联到 `tenant_id` 和 `owner_user_id`，再按需关联 `legal_user` 获取用户展示信息。

本次目标是参考 RAG 指标的日汇总批处理架构，新增 Token 消耗统计：定时任务默认在低峰期统计上一自然日，管理员可手动统计历史日期范围，前端按日期范围展示总消耗趋势和每日 Top 用户。

## 目标与非目标

**目标：**

- 每个租户、每个指标日期、每个统计版本维护一条 Token 消耗日汇总记录。
- 每个日汇总保存配置数量内的 Top 用户消耗明细，Top 数量由 YAML 配置控制。
- 支持低峰定时任务、手动历史日期范围统计、防重入、幂等跳过和失败重试。
- 支持按日期范围查询汇总卡片、趋势点、日汇总分页，并支持查看某日 Top 用户。
- 新增配置项、实体字段、枚举类和数据库字段均带中文说明注释。

**非目标：**

- 不在本次变更中改变模型调用方式或 Token 计费算法。
- 不将 Token 指标计算放入在线问答请求主链路。
- 不为每条消息新增指标扫描状态字段；Token 统计可通过 SQL 聚合幂等重算。
- 不统计第三方非聊天链路的 Token 消耗，除非该链路已写入 `chat_message.token_usage`。
- 不提供用户级费用结算，只提供运营监控和异常定位指标。

## 设计决策

1. 使用 `chat_message` + `chat_session` 作为统计来源。
   - 设计：按 `chat_message.created_at` 落入的自然日作为指标日期，通过 `chat_session` 获取租户和用户归属，仅统计当前租户会话内的消息 Token。
   - 口径：Token 总量使用 `SUM(GREATEST(token_usage, 0))`；消息数可统计参与聚合的助手消息数量，避免用户消息固定 0 稀释平均值。
   - 理由：复用已有在线写入字段，避免为 Token 指标新增实时埋点链路。
   - 替代方案：在模型调用处新增独立消费流水；该方案更精细，但改造面更大，且现有需求可先由消息表满足。

2. 使用日汇总主表承载看板统计结果。
   - 设计：新增 `token_usage_metric_daily_summary`，按 `tenant_id + metric_date + metric_version` 建唯一约束，保存总 Token、消息数、活跃用户数、平均每消息 Token、Top 用户数量、状态和时间字段。
   - 理由：日期范围查询可以直接聚合日汇总，不需要每次扫描大体量聊天消息。
   - 替代方案：看板实时聚合 `chat_message`；该方案随消息量增长会拖慢页面，并增加对在线表的读压力。

3. 使用 Top 用户子表保存每日排名结果。
   - 设计：新增 `token_usage_metric_top_user`，通过 `daily_summary_id` 关联日汇总，保存用户 ID、用户名、显示名、排名、Token 消耗、消息数、占比和统计版本。
   - 理由：Top 用户是日汇总的审计明细，独立子表便于分页、重新生成和后续扩展更多用户维度。
   - 替代方案：把 Top 用户 JSON 存入主表；该方案不利于查询、排序和展示字段演进。

4. 统计任务采用离线幂等重算，不修改源消息表扫描状态。
   - 设计：任务按租户和日期创建或复用日汇总；统计时先将日汇总置为 `PROCESSING`，聚合源数据后更新主表，并删除重建该日汇总下的 Top 用户明细。
   - 理由：Token 聚合是确定性 SQL 计算，不依赖 LLM 或外部系统，不需要像 RAG 指标一样逐条写扫描状态。
   - 替代方案：为 `chat_message` 增加扫描状态；该方案会放大在线表写入和迁移成本，不符合当前需求。

5. 定时任务沿用 RAG 指标低峰批处理风格。
   - 设计：新增 `TokenUsageMetricWorker`，默认 Cron 为 `0 0/5 2-5 * * ?`，默认处理上一自然日，使用本地 `AtomicBoolean` 防止单实例重入。
   - 批处理：`batch-size` 用于限制单轮最多处理多少个租户-日期任务；定时任务优先处理配置指标日期，再可选补扫更早未完成日期。
   - 理由：低峰运行减少对在线查询的影响，批处理便于大租户逐步完成。
   - 替代方案：每天固定跑一次全量统计；该方案失败后补偿不灵活，且不适合历史补扫。

6. 手动统计只允许今天之前的历史日期范围。
   - 设计：管理员通过 `/api/token-usage-metrics/run?date=...&endDate=...` 触发；结束日期必须早于服务器当前自然日；已完成且无强制重算需求时返回“已有记录，无需统计”。
   - 理由：当天数据仍在增长，避免展示口径随请求不断变化；历史统计具备稳定性。
   - 替代方案：允许统计当天；该方案适合实时监控，但与日归档指标口径冲突。

7. 状态与版本使用明确枚举和配置。
   - 设计：新增日汇总状态枚举，例如 `PROCESSING`、`COMPLETED`、`PARTIAL_FAILED`、`FAILED`；新增配置 `token.metric.usage.version` 或内部版本常量用于隔离统计口径变化。
   - 理由：状态枚举便于测试和排障，统计版本可避免未来口径变化污染历史看板。
   - 替代方案：只用字符串状态；该方案易产生拼写和兼容问题。

8. 前端使用独立 Token 指标看板。
   - 设计：新增页面或管理入口，卡片展示日期范围总 Token、消息数、活跃用户数、平均 Token；ECharts 展示每日 Token 与消息数趋势；日汇总表支持点击查看 Top 用户。
   - 理由：Token 成本指标与 RAG 质量指标关注点不同，独立页面更清晰。
   - 替代方案：混入 RAG 指标页面；该方案会让质量指标和成本指标耦合。

## 风险与权衡

- 在线表聚合读压力较高 → 增加 `chat_message(session_id, created_at)` 已有索引复用评估，必要时补充适配日期查询的索引；定时任务放在低峰期并限制批量。
- `chat_message` 无租户字段导致跨表聚合成本较高 → 通过 `chat_session` 连接获取租户和用户，后续如有性能瓶颈可考虑为消息表冗余租户字段。
- 只统计写入 `token_usage` 的消息会漏掉未记录用量的模型调用 → 本次明确口径为“已落库聊天消息 Token”，并在页面展示零值/未知用量不代表无成本。
- Top 用户排名可能因同分并列产生顺序差异 → 排序使用 Token 降序、消息数降序、用户 ID 升序保证稳定。
- 手动大范围统计可能长时间占用数据库 → 限制单次日期范围或按批执行，并在前端提示任务结果。
- 多实例部署下本地防重入不足 → 数据库唯一约束和状态更新保证幂等；如后续多实例并发明显，可引入分布式锁。

## 迁移计划

1. 新增 `token_usage_metric_daily_summary` 和 `token_usage_metric_top_user` 表，所有字段、索引和表注释完整记录统计口径。
2. 新增 Token 指标状态枚举、配置类、Entity、Mapper 和 DTO；每个实体属性和枚举值添加中文注释。
3. 在 `application.yaml` 新增 `token.metric.usage` 配置，所有条目添加中文注释，默认关闭或按产品要求开启。
4. 实现统计服务：创建/复用日汇总、聚合消息 Token、刷新 Top 用户、状态流转、手动日期范围校验和幂等跳过。
5. 实现定时 Worker 与管理 API，并复用当前管理员鉴权方式。
6. 新增前端 Token 指标页面和路由入口，展示趋势、日汇总、Top 用户和手动统计结果。
7. 灰度时先关闭自动任务，通过单日手动统计验证 SQL 聚合、表数据和页面展示，再开启低峰定时任务。
8. 回滚时关闭 `token.metric.usage.enabled`，保留新表数据；前端可隐藏入口，不影响在线问答。

## 发布与运维说明

### 统计口径

- 统计来源为 `chat_message.token_usage`，并通过 `chat_session.session_id` 关联租户与会话所属用户。
- 指标日期使用 `chat_message.created_at` 所属服务器自然日。
- 当前口径仅统计 `role = ASSISTANT` 的助手消息，空 Token 或未记录 Token 按 0 处理。
- Top 用户按 Token 消耗降序、消息数降序、用户 ID 升序排序，保证同分场景下排名稳定。

### YAML 配置

- `token.metric.usage.enabled` 控制定时任务开关。
- `token.metric.usage.version` 表示统计版本，用于隔离未来口径变化。
- `token.metric.usage.worker.cron` 控制定时任务触发时间。
- `token.metric.usage.worker.metric-date-offset-days` 控制默认统计距离当前日期多少天的业务日期。
- `token.metric.usage.worker.batch-size` 控制单轮最多处理多少个租户日期任务。
- `token.metric.usage.top-users.limit` 控制每日保留 Token 消耗最高的用户数量。

### 灰度与回滚

- 灰度时建议先保持定时任务关闭，使用手动接口统计单个历史日期并验证汇总表、Top 用户表和前端页面。
- 单日验证无误后，再开启低峰定时任务处理上一自然日。
- 回滚时关闭 `token.metric.usage.enabled`，保留新增表数据，前端可隐藏入口或停止访问 Token 指标接口。
