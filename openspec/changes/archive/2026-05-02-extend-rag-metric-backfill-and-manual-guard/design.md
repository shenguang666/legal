## 背景

当前 RAG 指标链路已经具备日汇总主表、消息级评估子表和 `retrieval_log` 扫描状态字段。定时任务通过 `RagRetrievalMetricWorker.runDailyEvaluation()` 调用 `RagRetrievalMetricService.evaluateDate(null)`，再由 `metricDateOffsetDays` 决定默认处理日期，当前默认是上一自然日。

这个模型可以稳定归档指定日期，但仍存在两个缺口：第一，定时任务完成上一自然日后，不会主动向更早日期回溯检查是否还有历史未检测、失败可重试或状态为空的 RAG 消息；第二，手动 `/api/rag-metrics/run` 可以评估任意日期，缺少“只能评估今天之前历史日期”的限制，也缺少目标日期已完成时的提示。

## 目标与非目标

**目标：**
- 定时任务仍优先归档配置日期，默认上一自然日。
- 配置日期没有待处理数据后，定时任务继续查找更早日期中仍需处理的 RAG 消息，并按批次补扫。
- 补扫消息按其 `retrieval_log.created_at` 所属业务日期归入对应日汇总，处理后刷新该日汇总平均召回率、平均精确率和计数。
- 明确扫描状态枚举语义：成功、失败、跳过/过滤等终态不重复处理；为空、待处理或失败且未超过重试次数表示仍需处理。
- 手动评估限制结束日期必须早于当前自然日，不允许评估今天或未来日期。
- 手动评估执行前检查目标日期是否已完整处理；如果已存在完成汇总且无待处理/可重试日志，返回提示而不是重复评估。

**非目标：**
- 不改变 Recall、Precision、TP、FN、FP 的计算公式。
- 不把离线评估放入在线 RAG 问答链路。
- 不强制重跑所有历史成功评估。
- 不引入新的外部任务调度系统。

## 设计决策

1. 定时任务拆分为“首选日期处理”和“历史补扫选择”。
   - 设计：Worker 每次运行先处理 `scheduledMetricDate()`；若该日期没有可处理日志或已经完成，再查询更早日期中最早或最需要补偿的一天进行处理。
   - 理由：保留当前前一自然日归档口径，同时让低峰任务自然消化历史积压。
   - 备选方案：一次任务扫描所有历史日期；该方案容易超过批大小和任务时间，不利于控制 LLM 成本。

2. 历史补扫以 `retrieval_log` 为准选择待处理日期。
   - 设计：查询 `hit_chunk_ids` 非空、`created_at` 小于首选日期起始时间，且扫描状态为空、待处理或失败未超过重试次数的日志，按业务日期升序或日志 ID 升序选择一个日期处理。
   - 理由：`retrieval_log` 是是否存在待评估 RAG 消息的事实来源，能覆盖没有日汇总记录的历史数据。
   - 备选方案：只扫描日汇总表中 `PROCESSING/PARTIAL_FAILED` 的日期；该方案无法发现从未创建过汇总的历史日志。

3. 处理结果仍通过日汇总主表重算。
   - 设计：每处理一条日志，都按日志所属日期获取或创建日汇总，评估完成后刷新该汇总的计数、平均召回率和平均精确率；日期处理结束后再判断是否完成。
   - 理由：补扫和重试会改变某个历史日期的成功/失败/跳过数量，必须重新计算聚合结果。
   - 备选方案：只增量累加计数；该方案在失败重试、删除旧失败评估、跳过状态变化时容易产生偏差。

4. 手动评估改为受保护的历史评估入口。
   - 设计：接口层或服务层校验结束日期必须早于 `LocalDate.now()`；如果目标日期范围已完成且没有待处理/可重试日志，返回“已有记录，无需评估”的结果状态或提示。
   - 理由：当天数据尚未完整，未来日期无数据意义；重复手动评估会浪费 LLM 成本并造成用户误解。
   - 备选方案：允许前端自行限制日期；该方案无法防止直接调用 API。

5. 扫描状态优先复用现有字段，必要时扩展枚举值。
   - 设计：优先复用 `retrieval_log.rag_metric_scan_status`、`rag_metric_scanned_at`、`rag_metric_summary_id`、`rag_metric_retry_count`、`rag_metric_error_message`。若实现时将过滤状态从 `FILTERED` 改为 `SKIPPED`，需要同步 Java 枚举、数据库字段注释、历史兼容映射和测试。
   - 理由：当前已有扫描状态字段和枚举，避免无意义新增重复字段。
   - 备选方案：新增另一个完成状态字段；该方案会造成状态来源分裂。

## 风险与权衡

- 历史积压过多导致补扫周期长：通过 `batch-size` 控制单次处理量，低峰任务多次运行逐步消化。
- 失败日志反复重试增加成本：继续使用 `max-retries` 限制，并在超过重试次数后不再自动处理。
- 手动评估与定时任务并发处理同一日期：实现时应复用日汇总幂等创建逻辑，并尽量通过状态更新避免重复评估同一日志。
- `FILTERED` 与用户期望的 `SKIPPED` 命名不一致：实现前需要决定是新增/迁移为 `SKIPPED`，还是在接口提示中统一展示为跳过；如果改枚举必须补充迁移兼容。
- 今天之前的边界受服务器时区影响：以应用服务器 `LocalDate.now()` 为准，并在接口错误信息中明确口径。

## 迁移计划

1. 新增或调整服务方法，用于判断指定日期是否存在待处理/可重试日志、是否已完整处理，以及查找更早历史待处理日期。
2. 改造定时 Worker 调用入口，使其先处理默认归档日期，再在可控批次内补扫历史日期。
3. 改造手动评估接口和 DTO，返回已处理提示、非法日期错误和实际处理统计。
4. 如需要新增或改名扫描状态枚举值，更新 Java 枚举、数据库字段注释、schema 文档和历史兼容逻辑。
5. 增加服务测试和接口测试，覆盖历史补扫、失败重试、日汇总重算、手动日期保护和已处理提示。
6. 发布后保持任务低峰运行，观察历史积压消化速度；如需回滚，可恢复 Worker 只处理默认日期，并保留已有扫描状态字段。

## 待确认问题

- 扫描状态是否必须把现有 `FILTERED` 改名为 `SKIPPED`，还是保留数据库值 `FILTERED`、前端展示为“跳过”。
- 手动评估是否只支持单日，还是扩展为开始日期到结束日期范围；用户已明确提到“结束日期”，实现时建议支持范围并兼容单日。
