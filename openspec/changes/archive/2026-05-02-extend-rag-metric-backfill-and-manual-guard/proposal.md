## 背景与原因

当前 RAG 指标定时任务只处理一个配置日期，默认上一自然日；如果更早日期存在 `retrieval_log` 未检测、检测失败或历史遗留为空状态的 RAG 消息，需要依赖人工逐日补跑，容易造成日汇总指标长期不完整。手动评估接口也缺少日期上限和已处理检查，可能误评估今天或未来日期，或者对已完成日期重复发起评估。

## 变更内容

- 调整 RAG 指标定时任务流程：优先处理当前配置的归档日期，默认仍为前一个自然日；处理完后继续检查更早业务日期是否存在未检测或可重试的 RAG 消息，并按批次补扫。
- 明确 `retrieval_log` 的 RAG 指标扫描状态语义：使用枚举状态标记 `SUCCESS`、`FAILED`、`SKIPPED` 等终态；为空、待处理或可重试失败表示仍需处理。
- 对补扫处理过的消息，按消息所属业务日期找到或创建对应日汇总，并在处理后重新计算该日期的平均召回率、平均精确率和计数指标。
- 调整手动评估能力：手动评估结束日期不能大于等于当日，只允许评估今天之前的历史日期。
- 手动评估在执行前需要检查目标日期范围是否已被定时任务或历史评估完整处理；如果已有完成记录且没有未处理/可重试消息，应返回明确提示，避免重复评估。
- 保留当前低峰定时、批大小、失败重试、低质量 query 过滤、粗召回 + 精筛和严格 LLM 失败策略。

## 能力范围

### 新增能力
- 无。

### 修改能力
- `rag-retrieval-daily-metrics`：扩展日指标定时任务从单日归档升级为“当前归档日优先 + 历史未处理补扫”；增加手动评估日期保护和已处理提示。

## 影响范围

- 后端服务：改造 `RagRetrievalMetricService.evaluateDate`、定时 Worker 调度入口、日志选择逻辑、日汇总刷新和完成判断。
- 后端接口：调整 `/api/rag-metrics/run` 手动评估参数与校验逻辑，支持返回“已处理无需评估”的结果或提示。
- DTO/枚举：可能需要扩展 `RunResult`，补充跳过原因、已完成提示、处理日期范围、补扫日期等信息；如新增字段需添加注释。
- 数据库：优先复用已有 `retrieval_log.rag_metric_scan_status`、`rag_metric_scanned_at`、`rag_metric_summary_id`、`rag_metric_retry_count` 和 `rag_metric_error_message`；如新增字段或枚举值，必须补充数据库字段注释和 Java 枚举注释。
- 测试：需要覆盖定时补扫历史未处理消息、失败重试、日汇总重算、手动评估日期上限、已完成日期重复评估提示等场景。
