## 背景与原因

现有 RAG 指标评估以明细样本为中心，无法稳定表达每日企业级统计结果，且旧方案仍保留每日扫描条数上限、缺少 `retrieval_log` 扫描完成状态、状态字段未统一枚举化。需要将 RAG 指标升级为日汇总主表 + 消息级明细子表的批处理模型，保证定时任务能覆盖当天所有有效 RAG 消息，并为运营看板提供可审计、可追踪、可扩展的数据基础。

## 变更内容

- 新增 RAG 指标日汇总主表：每天每个租户生成一条汇总记录，保存平均召回率、平均精确率、使用过 RAG 的消息数、有效消息数、过滤消息数、成功/失败/跳过数量、任务状态和统计窗口。
- 改造 `rag_retrieval_metric_evaluation` 为消息级评估子表：增加日汇总主表外键，保留每条消息的 TP/FN/FP、Recall、Precision、LLM 判断结果、错误信息和状态。
- 扩展 `retrieval_log`：新增 RAG 指标扫描状态、扫描时间、关联评估批次或日汇总标识等字段，用于防止重复扫描并追踪定时任务完成情况。
- 将所有指标相关状态字段改为枚举语义：包括检索日志扫描状态、日汇总任务状态、消息级评估状态；Java 枚举类和数据库字段注释必须说明取值含义。
- 移除每日扫描条数上限 `max-daily-samples`：定时任务应统计当天所有使用过 RAG 且未被过滤的消息，同时记录总消息数和有效消息数。
- 调整定时任务策略：默认在业务低峰期 02:00-05:00 每 5 分钟执行一次，增量扫描 `retrieval_log` 当天数据，支持失败重试和幂等补偿。
- 调整统计 API：日期范围查询直接读取日汇总结果集，并在服务端聚合出总召回率、总精确率、消息条数、有效消息条数、失败条数等指标。
- 调整前端 RAG 指标页面：使用 ECharts 展示日维度召回率、精确率、消息量、有效消息量趋势，并支持查看某日汇总下的消息级明细。
- 保留低质量 query 过滤、LLM 严格失败、粗召回 + 精筛判断等已有质量控制策略，并使过滤结果参与日汇总统计。

## 能力范围

### 新增能力
- `rag-retrieval-daily-metrics`：RAG 检索质量日汇总、检索日志扫描状态、消息级评估子表、定时增量统计、日期范围聚合和趋势图能力。

### 修改能力
- 无。

## 影响范围

- 后端：新增日汇总 Entity/Mapper/Service，改造评估服务、定时任务、统计 API、DTO 和枚举类。
- 数据库：新增 RAG 指标日汇总表，改造 `rag_retrieval_metric_evaluation` 增加主表外键，改造 `retrieval_log` 增加扫描状态相关字段和索引。
- 配置：移除或废弃 `max-daily-samples`，调整默认 Cron 为低峰期 02:00-05:00 每 5 分钟运行，并保留开关、批大小、候选召回和 LLM 判断配置。
- 前端：改造 RAG 指标页面的数据源、卡片指标、趋势图和明细表交互，引入或复用 ECharts。
- 运维：定时任务会覆盖当天所有 RAG 消息，需要考虑大模型成本、ES 压力、任务锁、失败重试、幂等和历史数据迁移。
