## 背景

现有 RAG 指标功能以 `rag_retrieval_metric_evaluation` 明细表为核心，统计接口实时扫描明细并计算平均召回率、平均精确率。该模型适合小样本验证，但不适合企业级日统计：缺少稳定的日汇总结果、无法追踪 `retrieval_log` 是否已被定时任务扫描、状态值是字符串而非枚举语义、每日样本上限会导致统计不完整。

新的目标是把指标链路升级为检索日志扫描状态 + 日汇总主表 + 消息级评估子表的批处理模型。定时任务在低峰期增量扫描 `retrieval_log`，对当天业务日期内使用过 RAG 的消息进行过滤、评估和汇总，并为前端趋势图提供稳定的数据源。

## 目标与非目标

**目标：**
- 每个租户、每个业务日期、每个评估版本维护一条 RAG 指标日汇总记录。
- `rag_retrieval_metric_evaluation` 作为消息级子表，增加日汇总主表外键。
- `retrieval_log` 增加指标扫描状态字段，支持幂等扫描、失败重试和完成追踪。
- 所有状态字段在 Java 中使用带注释的枚举类表达，并在数据库字段注释中列出取值含义。
- 移除每日最大扫描样本数限制，定时任务覆盖当天所有使用过 RAG 且符合过滤条件的消息。
- 定时任务默认在 02:00-05:00 每 5 分钟执行一次，按批增量处理未完成日志。
- 日期范围统计读取日汇总结果集并聚合，前端使用 ECharts 展示趋势。

**非目标：**
- 不把离线指标计算放入在线问答请求链路。
- 不在本次变更中实现人工标注平台或人工复核工作流。
- 不强制修改在线 RAG 检索排序算法。
- 不删除历史明细数据；旧版本数据通过评估版本隔离。

## 设计决策

1. 使用日汇总主表承载看板统计结果。
   - 设计：新增 `rag_retrieval_metric_daily_summary`，按 `tenant_id + metric_date + evaluation_version` 建唯一约束。
   - 理由：日期范围查询可以直接聚合日结果，避免每次页面加载扫描大量消息级明细。
   - 替代方案：继续实时聚合子表；该方案在企业数据量下查询成本高，且无法表达定时任务执行状态。

2. 保留 `rag_retrieval_metric_evaluation` 作为消息级子表。
   - 设计：新增 `daily_summary_id` 外键关联日汇总主表，明细仍保存 query、chunk IDs、TP/FN/FP、Recall、Precision、LLM 原始输出、解释、错误信息和状态。
   - 理由：主表负责趋势和汇总，子表负责审计和问题排查。
   - 替代方案：把明细 JSON 聚合到主表；该方案不利于分页、失败重跑和排查单条消息。

3. 在 `retrieval_log` 增加扫描状态而不是只靠评估表幂等判断。
   - 设计：新增 `rag_metric_scan_status`、`rag_metric_scanned_at`、`rag_metric_summary_id`、`rag_metric_error_message` 等字段。
   - 理由：可以快速知道日志是否已被任务处理，也便于失败重试和运维排查。
   - 替代方案：只查子表是否存在；该方案无法区分过滤、失败、处理中、待处理等状态。

4. 状态字段统一枚举语义。
   - 设计：新增 Java 枚举，例如 `RagMetricScanStatusEnum`、`RagMetricDailyStatusEnum`、`RagMetricEvaluationStatusEnum`，枚举类和枚举值均添加注释。
   - 数据库字段仍建议使用 `VARCHAR`，字段注释列出枚举取值。
   - 理由：Java 枚举提升代码可读性和约束力，数据库 `VARCHAR` 比 MySQL `ENUM` 更易扩展。
   - 替代方案：数据库 ENUM；该方案迁移成本较高，新增状态需要 DDL。

5. 定时任务采用低峰期增量批处理。
   - 设计：默认 Cron 使用 `0 0/5 2-5 * * ?`，每 5 分钟处理一批 `retrieval_log` 中未完成的目标业务日期数据。
   - 统计日期：默认处理上一自然日，避免当天数据尚未完整；支持手动 API 指定日期重算，也可通过配置切换日期偏移。
   - 理由：降低对在线业务、ES 和 LLM 的影响，并允许大数据量分片完成。
   - 替代方案：单次任务全量跑完；该方案容易超时，失败后补偿成本高。

6. 移除 `max-daily-samples`，保留批大小和任务锁。
   - 设计：不再限制每日扫描总数；`batch-size` 只限制单轮处理量。任务多次运行直到当天全部日志进入终态。
   - 理由：企业级指标应覆盖全量有效消息，不能抽样替代日统计。
   - 替代方案：继续样本上限；该方案会导致消息量和指标统计不完整。

7. 汇总指标按成功明细计算，过滤和失败单独计数。
   - 设计：日均 Recall/Precision 基于 `SUCCESS` 子表平均；总消息数统计使用过 RAG 的日志数；有效消息数排除过滤项；过滤、失败、跳过单独计数。
   - 理由：避免失败样本污染质量指标，同时保留任务质量和数据覆盖度。
   - 替代方案：失败按 0 分计入平均；该方案会混淆检索质量和评估系统可用性。

8. 前端趋势图以日汇总 API 为数据源。
   - 设计：summary API 返回卡片指标和 daily trend，detail API 按 `daily_summary_id` 或日期范围分页查询子表。
   - 理由：趋势图加载稳定，明细排查按需加载。
   - 替代方案：前端请求全部明细后本地聚合；该方案数据量不可控。

## 风险与权衡

- 大模型成本随全量消息增长：使用低峰期、单轮批大小、任务锁、失败重试、粗召回 + 精筛比例控制成本。
- 日任务可能在 05:00 前未跑完：保留未完成状态，下一个低峰窗口继续增量处理，并提供手动补偿接口。
- `retrieval_log` 表结构变更影响在线写入：新字段必须可空或有默认值，新增索引避免锁表风险。
- 旧明细没有 `daily_summary_id`：通过新评估版本隔离；如需历史迁移，提供可选回填脚本。
- 状态枚举扩展与数据库字段不一致：字段注释和 Java 枚举同步更新，测试覆盖状态映射。
- 统计日期当天/前一天口径易混淆：文档和 UI 显示业务日期，默认前一天，可通过手动接口指定。

## 迁移计划

1. 新增日汇总表，包含租户、业务日期、评估版本、消息计数、平均指标、状态、错误信息和时间字段，所有字段添加注释。
2. 修改 `rag_retrieval_metric_evaluation`，增加 `daily_summary_id` 外键和必要索引。
3. 修改 `retrieval_log`，增加 RAG 指标扫描状态、扫描时间、关联汇总 ID、错误信息等字段，所有字段添加注释。
4. 新增状态枚举类并替换散落字符串状态判断。
5. 调整配置，删除或废弃 `max-daily-samples`，默认 Cron 改为 `0 0/5 2-5 * * ?`。
6. 改造定时任务为增量批处理：创建或锁定日汇总记录，扫描待处理日志，写入子表，更新日志状态，刷新日汇总。
7. 改造统计 API 和前端 ECharts 趋势图。
8. 灰度运行：先关闭自动任务，手动触发单日小范围验证，再开启低峰自动任务。
9. 回滚：关闭任务开关；保留新表和字段；前端可临时切回旧明细聚合页面或隐藏入口。

## 待确认问题

- 业务日期默认处理上一自然日还是任务运行当日：建议默认上一自然日，手动接口支持指定日期。
- 是否需要按知识库、用户、模型或检索来源扩展日汇总维度：本次先按租户 + 日期 + 评估版本，后续可新增维度列。
- 旧 `rag-metric-v1/v2` 明细是否需要回填主表：建议不回填，保留审计；新版本开始按主子表模型运行。
