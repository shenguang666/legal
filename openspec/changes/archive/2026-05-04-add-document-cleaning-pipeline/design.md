## Context

当前文档导入能力已经支持原生解析和 MinerU 精准解析，并会将解析结果切块后写入 `kb_chunk`，再通过 outbox 进入 Elasticsearch 索引。现有链路的主要问题是解析器输出会直接参与切块：

- 原生解析：`DocumentTextExtractor -> DocumentChunker -> completeNative -> kb_chunk`。
- MinerU 解析：`MineruClient.downloadMarkdown -> SemanticDocumentChunker -> completeDocument -> kb_chunk`。

PDF、Word 和官网导出文件中常见页眉、页脚、页码、版权声明、下载时间、官网链接、系统导出说明等内容。如果这些噪声进入 `kb_chunk`，会降低向量召回和关键词检索质量，也会让 RAG 答案引用无关证据。

本设计需要在不破坏现有解析方式、索引路由和异步解析任务的前提下，为所有解析结果提供统一清洗能力。

## Goals / Non-Goals

**Goals:**

- 在文档解析后、切块前统一清洗原生文本和 MinerU Markdown。
- 删除或过滤页码、重复页眉页脚、版权信息、官网导出元数据、孤立 URL 等低价值内容。
- 在切块后过滤明显低质量切片，避免脏数据入库和索引。
- 保留合同标题、章节标题、法律条款编号、表格证据等高价值内容。
- 提供可配置开关和阈值，便于不同部署环境按需调整。
- 输出清洗摘要，支持日志排查、测试验证和后续质量评估。

**Non-Goals:**

- 不在本变更中实现完整 OCR 或版面理解能力。
- 不引入新的外部清洗服务或大模型清洗依赖。
- 不改变用户选择 NATIVE 或 MINERU_PRECISE 的现有交互语义。
- 不改变知识库索引路由、RAG 检索范围和 MinerU 凭证管理能力。
- 不强制新增前端清洗预览；如需要可作为后续增强。

## Decisions

### Decision 1: 在解析后、切块前增加统一清洗层

采用 `DocumentContentCleaner` 作为统一入口，分别支持纯文本和 Markdown 输入。原生解析先执行文本抽取，再清洗，再切块；MinerU 先下载 Markdown，再清洗，再语义切块。

理由：

- 切块前清洗可以避免噪声影响块边界和 embedding 内容。
- 两种解析方式共享清洗策略，避免规则重复。
- 清洗层与解析器、切块器解耦，便于测试和配置。

备选方案：只在切块后过滤。该方案实现简单，但噪声仍可能改变切块边界，并污染相邻正文切片，因此不作为主方案。

### Decision 2: 使用规则清洗，不引入大模型清洗

清洗策略优先使用确定性规则：基础规范化、重复行统计、页眉页脚候选识别、内置噪声正则、低质量切片评分。

理由：

- 文档入库流程需要稳定、可解释、低成本。
- 大模型清洗可能误删正文，且增加延迟和费用。
- 规则结果可通过清洗摘要解释，便于回归测试。

备选方案：使用 LLM 判断每行是否噪声。该方案不稳定且成本高，可作为未来人工审核或离线清洗增强，不纳入本次范围。

### Decision 3: 重复页眉页脚采用“位置 + 频率 + 长度”联合判断

清洗器按页或按近似分页块统计页面首尾若干行，只有满足以下条件的行才作为重复噪声候选：

- 出现次数达到最小阈值。
- 出现页面比例达到阈值。
- 主要出现在页首或页尾扫描范围内。
- 行长度低于阈值，或命中页码、版权、来源、导出元数据等低价值模式。

理由：

- 只按重复次数删除容易误删合同模板中重复出现的正文条款。
- 加入位置和低价值模式后可以降低误删风险。

### Decision 4: 对法律短标题采用保护策略

短文本不直接删除。若短行符合章节标题、法律条款编号、合同常见标题或 Markdown 标题结构，应保留并交给语义切片器处理。

理由：

- 法律文档中“违约责任”“争议解决”“付款条款”等短标题对检索非常关键。
- 切块后过滤必须区分低价值短文本和高价值章节标题。

### Decision 5: 清洗摘要先以服务内对象和日志为主，数据库持久化作为可选增强

MVP 阶段生成 `DocumentCleaningReport`，记录原始字符数、清洗后字符数、删除行数、删除原因计数和删除样例。默认写入日志并可在测试中断言。是否新增清洗日志表由实现阶段结合现有数据库改动成本决定。

理由：

- 清洗能力本身不依赖新表即可工作。
- 日志和对象摘要足够支持初期验证。
- 如果后续要前端展示清洗明细，再新增数据库表更稳妥。

### Decision 6: 配置默认开启低风险规则

新增 `legal.document-processing.cleaning` 配置组，默认启用基础规范化、页码过滤、导出元数据过滤、重复页眉页脚过滤和低质量切片过滤。所有新增 YAML 配置项必须逐条添加中文注释。

理由：

- 用户导入官网导出 PDF 时默认应获得更干净的检索效果。
- 可配置开关支持在误删风险较高时回退。

## Risks / Trade-offs

- **误删正文重复条款** → 清洗重复行时必须联合位置、频率、长度和低价值模式判断；测试需要覆盖重复正文保留场景。
- **误删法律短标题** → 切块后过滤必须保护章节标题、编号条款和合同常见标题。
- **分页边界不稳定** → 当解析结果缺少明确分页符时，清洗器只能退化为全局重复短行和模式过滤，不强行推断页面结构。
- **MinerU Markdown 结构被破坏** → Markdown 清洗必须保留标题、表格、列表和编号条款结构，不得简单合并所有换行。
- **配置过多增加理解成本** → 默认提供安全配置，前期只暴露必要开关和阈值，复杂租户级规则后续再扩展。
- **清洗效果难量化** → 清洗摘要和测试样例需要记录删除原因统计，并通过 RAG 召回指标后续观察效果。

## Migration Plan

1. 新增清洗配置类字段，并在 `application.yaml` 添加带中文注释的默认配置。
2. 新增清洗器和质量过滤器，先通过单元测试验证规则行为。
3. 接入原生解析链路：文本抽取后、切块前执行清洗。
4. 接入 MinerU 链路：Markdown 下载后、语义切块前执行清洗。
5. 在持久化 `kb_chunk` 前执行低质量切片过滤。
6. 编译和测试通过后部署；如发现误删，可通过配置关闭清洗或关闭特定规则。

## Open Questions

- 是否需要在首版新增 `kb_document_cleaning_log` 表持久化清洗摘要，还是先使用日志和内存报告？ ask：可以，就是清洗掉的内容可以保存，避免误删后无法排查
- 前端是否需要提供“清洗开关”或“清洗摘要展示”，还是保持后端默认清洗？ ask：需要前端展示清洗是否需要清洗，因为有些文档已经人工处理过了，或者说用户不希望清洗掉某些内容，所以前端可以提供开关，默认关闭，用户可以选择开启
- 是否需要支持租户级自定义噪声正则，例如某些企业固定导出页眉？  ask：建议后续版本再支持，首版先提供丰富的内置规则和配置项，满足大部分场景。
