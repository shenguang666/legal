## 背景与现状

当前系统已经具备：短期记忆缓存、会话摘要、长期记忆表、用户外挂知识表、异步 outbox worker、以及 `legal_kb_user_knowledge` ES 索引。但现有实现仍然偏“直觉式自动化”：长期记忆在部分链路中仍容易受到单轮对话影响，外挂知识库也缺乏严格的三级分类、延迟复核和候选治理，容易产生知识污染、重复入库和错误画像。

本次变更属于跨模块改造：涉及 `chat`、`memory`、`retrieval`、`config`、MySQL 表结构、ES 索引写入策略，以及异步 worker 触发顺序。由于项目当前使用 Spring Boot + MyBatis-Plus + Redis + Elasticsearch + LangChain4j，并已采用 outbox 模式处理异步索引，因此设计需要在现有架构上演进，而不是引入全新组件。

## 目标 / 非目标

**目标：**
- 将长期记忆重构为“摘要驱动 + 候选态 + 连续命中确认 + 稳定升级”的谨慎机制。
- 对长期记忆键做规范化与冲突合并，避免 `job/职业/profession` 之类语义重复键并存。
- 将外挂知识库重构为“规则预过滤 + LLM 三级分类 + must 立即入库 + optional 延迟复核”的流程。
- 为外挂知识与长期记忆补充更完整的状态流转与元数据，支持候选、复核、升级和治理。
- 继续复用现有 `memory_task_outbox`、Redis、MySQL、Elasticsearch 的技术栈，不新增外部基础设施。

**非目标：**
- 不在本次变更中引入新的前端配置页或人工审核后台。
- 不在本次变更中实现跨租户共享的个人外挂知识库。
- 不替换现有 RAG 主检索链路，只增强用户私有记忆/知识的治理方式。

## 关键决策

### 1. 长期记忆只从摘要中识别，不再逐轮识别
- 选择：长期记忆抽取仅在 `SUMMARY_REFRESH` 后执行，输入为会话摘要，而不是单轮问答。
- 原因：长期画像应基于阶段性稳定信号，不能被单句随口表达驱动。
- 备选方案：逐轮抽取 + 置信度过滤。
- 放弃原因：即使加阈值，单轮信息仍容易产生噪声，且模型调用频率高。

### 2. 长期记忆引入候选态与连续命中确认
- 选择：长期记忆写入先进入候选态，记录命中次数；只有连续多次摘要都识别到同一 canonical key/value，才升级为稳定记忆。
- 原因：稳定画像不能依赖单次识别；候选态可以吸收短期波动。
- 备选方案：首次命中直接 ACTIVE。
- 放弃原因：过于草率，容易污染系统提示词。

### 3. 长期记忆键统一 canonical key 映射
- 选择：引入固定别名映射表，将 `job/职业/profession` 统一为 `profession`，`身份/identity` 统一为 `identity`，`情绪/情感/emotion` 统一为 `emotion`。
- 原因：避免语义重复键并存，降低冲突处理复杂度。
- 备选方案：完全依赖模型输出标准键。
- 放弃原因：模型输出不稳定，无法保证长期一致性。

### 4. 外挂知识库采用三级分类与延迟复核
- 选择：对问答块先做规则预过滤，再做 `must/optional/forbidden` 分类。
  - `must`：立即入库并索引
  - `optional`：先存为候选/PENDING，等摘要阶段结合全局上下文复核
  - `forbidden`：直接丢弃
- 原因：避免把临时上下文、寒暄和低价值内容写入 ES。
- 备选方案：所有内容先入库，后续依赖去重清理。
- 放弃原因：会放大知识污染，增加 ES 噪声和检索误命中。

### 5. 继续复用 `memory_task_outbox` 作为统一异步编排器
- 选择：摘要刷新、长期记忆候选升级、外挂知识候选复核、即时入库等都通过现有 `memory_task_outbox` 串联。
- 原因：项目已有 outbox 模式，复用可以降低额外复杂度，保持一致的失败重试模型。
- 备选方案：拆成独立长期记忆 outbox 和知识治理 outbox。
- 放弃原因：当前变更规模下不值得再拆一层调度基础设施。

## 风险 / 权衡

- [摘要质量不足导致长期记忆误判] → 通过候选态、连续命中确认和 canonical key 冲突保护降低误判。
- [optional 候选积压导致数据库膨胀] → 增加候选状态、复核时间、后续可加 TTL/归档策略。
- [must 立即写入仍可能误分类] → 叠加规则预过滤、去重检查、核心内容提炼，降低误写风险。
- [摘要刷新频率过低导致长期记忆更新变慢] → 通过可配置 `refresh-rounds` 平衡准确性与时效性。
- [状态机更复杂导致实现复杂度上升] → 用明确字段和 worker 顺序约束流程，避免同步链路变重。

## 迁移计划

1. 扩展 `user_memory_item`：增加候选命中/稳定升级相关字段。
2. 扩展 `user_knowledge`：增加 `knowledge_level`、`reason`、`core_content`、`reviewed_at` 及更明确的状态语义。
3. 调整 `MemoryTaskService` 和 `MemoryTaskOutboxWorker`：让长期记忆只在摘要后抽取，让 optional 知识在摘要后复核。
4. 调整 `LongTermMemoryExtractionService`：从“摘要抽取 + 候选升级”视角实现，不再直接逐轮 ACTIVE。
5. 调整 `UserKnowledgeService`：实现三级分类、去重、即时写入/延迟复核逻辑。
6. 部署后允许旧数据继续存在；新逻辑只影响新增任务和新写入数据。
7. 如需回滚，可停用 `legal.memory.worker.enabled` 或回退服务代码，数据库新字段可兼容保留。

## 待确认问题

- 连续命中确认的升级阈值是否固定为 2，还是做成配置项？答：可以通过 YAML 文件配置。
- `optional` 候选在多久未被复核命中后应自动清理或归档？答：如果该会话 2 小时未更新，可视为用户已经退出该会话，这时可通过定时任务归档。
- 对于长期记忆冲突值，除置信度外是否还需要“最近命中时间 + 多次一致性”联合决策？答：可以考虑加入“最近命中时间 + 多次一致性”作为辅助决策因素，避免长期记忆被偶尔高置信度但过时的信息覆盖。
