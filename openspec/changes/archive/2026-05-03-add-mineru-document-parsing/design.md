## Context

当前项目的文档导入链路主要服务于知识库、风险规则和天眼审查三类场景。后端通过 `MultipartFile` 接收上传文件，使用 `DocumentTextExtractor` 基于 Apache Tika 抽取纯文本，再由 `DocumentChunker` 按固定字符长度切片并写入 `kb_document` / `kb_chunk`，部分业务再投递 ES 索引出站任务。

该方案实现简单、速度快，但对合同 PDF、扫描件、复杂表格、条款列表和多级标题的结构保留不足。固定字符窗口还会把句子、条款或表格行切断，导致 RAG 检索命中的证据片段不完整，影响合同字段抽取、风险规则匹配和用户对回答依据的信任。

MinerU v4 Precision Extract API 提供更强的版面解析能力，可输出 Markdown 和结构化 JSON。接入时需要处理外部 Token、安全配置、文件上传 URL、异步解析轮询、结果 zip 下载、失败重试和前端状态展示。项目规则还要求新增 YAML 配置项、实体属性和数据库字段必须有中文注释。

## Goals / Non-Goals

**Goals:**
- 保留现有原生解析流程，新增 MinerU 精准解析作为可选解析方式。
- 在知识库、风险规则和天眼审查文档上传入口提供统一解析方式选择。
- 默认将 MinerU 解析参数配置为精准解析路径，优先使用 v4 Precision Extract API 和 `model_version=vlm`。
- 将最大上传文档数量放入 YAML 配置，并在后端强校验、前端提示。
- 基于 MinerU Markdown/结构化结果实现更稳定的语义切片，减少断句和证据不完整。
- 避免在上传请求和数据库事务中长时间轮询 MinerU，支持状态查询、失败原因和重试。

**Non-Goals:**
- 首期不实现在线预览 MinerU 版面坐标、图片裁剪或逐页可视化标注。
- 首期不把 MinerU JSON 的所有结构字段完整映射为独立业务表。
- 首期不建设通用解析规则编辑器或复杂 chunk 策略配置 UI。
- 首期不强制重解析历史文档，历史文档仍按原有方式保留。
- 首期不在前端暴露 MinerU Token 或允许用户自行输入第三方凭证。

## Decisions

### 1. 使用可插拔解析器抽象统一原生解析和 MinerU 解析

新增统一解析接口，输入上传文件和解析上下文，输出标准化解析结果，例如原文、Markdown、结构块、解析方式、外部任务 ID 和错误信息。现有 `DocumentTextExtractor` 可作为 `NATIVE` 解析策略，MinerU 客户端作为 `MINERU_PRECISE` 解析策略。

**理由：** 三条导入链路当前存在相似代码，解析方式选择如果散落在各 service 中会增加重复逻辑。解析器抽象可以让知识库、风险规则、天眼审查共享同一策略分发、校验和错误处理。

**备选方案：**
- 只在每个 service 中加 `if parseMethod == MINERU`：实现快，但重复逻辑多，后续新增解析器成本高。
- 直接替换现有 Tika：破坏兼容性，也不适合 txt/md/docx 等轻量场景。

### 2. MinerU 采用后端异步解析任务，不在上传接口中同步轮询完成

上传接口负责校验文件、创建文档和解析任务，返回文档状态。后台 worker 负责调用 MinerU：申请上传 URL、PUT 文件、轮询 `extract-results`、下载结果 zip、读取 `full.md` 或结构化 JSON、执行切片并更新文档状态。

**理由：** MinerU 解析依赖外部服务，耗时不可控。同步轮询会导致请求超时和数据库事务长时间持有，也不利于失败重试和状态展示。异步模型与项目已有 ES outbox、合同审阅 worker 的思路一致。

**备选方案：**
- 同步等待 MinerU 解析完成：首期代码更少，但长文档、排队和网络抖动时稳定性差。
- 完全依赖 MinerU callback：实时性好，但需要公网可访问回调地址和签名校验，部署复杂度更高，可作为后续增强。

### 3. MinerU 默认走 v4 Precision Extract API

默认配置使用 `https://mineru.net/api/v4/file-urls/batch` 申请上传 URL，通过 `Authorization: Bearer <token>` 鉴权，上传完成后轮询 `/api/v4/extract-results/batch/{batch_id}`。默认 `model_version=vlm`、`language=ch`、`enable_table=true`、`enable_formula=true`，并保留 YAML 配置覆盖能力。

**理由：** 文档说明将 v4 Token 接口称为 Precision Extract API，并支持批量、本地文件上传、复杂表格和公式识别，符合“MinerU 默认用精准解析”的诉求。

**备选方案：**
- 使用轻量 Agent API：接入更简单，但能力和限流更适合 Agent 轻量场景，不适合作为后台文档导入的主路径。
- 仅支持 URL 解析：要求系统先把上传文件转成公网 URL，增加对象存储依赖和安全暴露面。

### 4. 对 MinerU 结果使用结构优先的语义切片

对 MinerU 输出优先读取 `full.md`，必要时结合 `content_list.json`、`layout.json` 识别标题、段落、列表、表格和公式块。切片时先按结构块组织，再按最大字符数合并相邻短块；超长块按句号、分号、换行、条款编号等边界二次切分，最后才退化到安全字符窗口。

**理由：** MinerU 解决的是文档结构解析，但检索质量还依赖切片策略。如果继续固定 `substring`，仍可能断句。结构优先切片可以保留合同条款、表格上下文和证据完整性。

**备选方案：**
- MinerU Markdown 直接整体入库：长文档 chunk 过大，检索粒度差，embedding 成本高。
- 仅按 Markdown 标题切分：标题下内容可能过长或过短，需要结合长度约束。

### 5. 上传数量由 YAML 配置控制并后端强校验

新增文档处理配置属性，至少包含最大上传文档数量、单文件大小沿用 Spring multipart 限制或单独配置、解析方式默认值、MinerU 开关和超时轮询参数。前端读取配置或通过后端能力接口获取限制，用于 UI 提示；后端始终执行最终校验。

**理由：** 前端校验只能改善体验，不能作为安全边界。YAML 配置便于不同环境根据 MinerU 成本、队列能力和业务场景调整。

**备选方案：**
- 写死上传数量：无法适配生产和测试环境差异。
- 只做前端限制：可被绕过，不满足后端安全要求。

### 6. 解析元数据需要持久化以支持排查和重试

建议扩展 `kb_document` 或新增 `kb_document_parse_task` 表，保存解析方式、解析状态、MinerU batch ID、data ID、结果 URL、失败原因、重试次数、开始/完成时间。若新增字段或实体属性，必须按项目规则添加中文注释。

**理由：** MinerU 是异步外部依赖，只有持久化任务状态才能支持页面进度、失败排查、幂等重试和后续审计。

**备选方案：**
- 仅在内存中记录任务：服务重启后状态丢失。
- 仅依赖日志：前端无法展示状态，失败重试也难以自动化。

## Risks / Trade-offs

- **MinerU 外部服务不可用或超时** → 提供开关、超时、重试、失败状态和原生解析回退提示。
- **解析成本和队列耗时增加** → 上传数量、worker 并发、轮询间隔和超时时间均通过 YAML 控制。
- **Markdown 切片仍可能不完美** → 使用结构块优先、句子边界二次切分和测试样本持续调优。
- **Token 泄露风险** → Token 只允许后端环境变量配置，不返回前端，不写入日志。
- **数据库状态复杂度上升** → 明确定义解析状态流转，并在失败时保留可读错误原因。
- **前端批量上传体验复杂** → 首期可以先在单入口中支持多文件选择和数量限制，状态列表后续逐步增强。
- **历史文档解析方式不一致** → 文档列表展示解析方式或默认历史文档为 `NATIVE`，不强制迁移。

## Migration Plan

1. 新增配置属性和 YAML 配置，默认关闭 MinerU 或要求 Token 存在才允许选择 MinerU。
2. 扩展数据库 schema 或新增解析任务表，所有新增字段添加中文注释。
3. 引入解析方式枚举、解析状态枚举、解析器接口、原生解析器和 MinerU 客户端。
4. 改造知识库、风险规则和天眼审查导入链路，使其创建解析任务并根据解析完成结果写入切片。
5. 新增或复用后台 worker 执行 MinerU 异步解析和语义切片。
6. 前端上传页面增加解析方式选择、数量限制提示、状态展示和失败提示。
7. 使用原生解析、MinerU 成功、MinerU 失败、超限上传、未配置 Token 等场景验证。
8. 回滚时关闭 MinerU 配置，前端隐藏 MinerU 选项，后端继续允许原生解析导入。

## Open Questions

- 批量上传首期是否要求三个入口全部支持，还是先支持知识库上传后再推广到风险规则和天眼审查。
- MinerU 失败时是否允许自动回退到原生解析，还是必须由用户确认后重试，避免用户误以为已完成精准解析。
- 是否需要单独的后端能力接口向前端返回 `mineruEnabled`、默认解析方式和最大上传数量。
- 是否需要保存 MinerU 原始 zip 或仅保存解析后的 Markdown/切片结果。
